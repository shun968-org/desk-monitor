# ADRの作成・更新

このリポジトリが作っているもの自体のアーキテクチャ（実装上の技術選定）に関する判断根拠を
`docs/adr/` に **Nygard形式** で記録する。

**ブランチ運用・コミット規約・PRフローなどのプロジェクトルール／開発プロセスの決定はここに書かない。**
それらは [`CONTRIBUTING.md`](../../../CONTRIBUTING.md) に記載する。

一覧は持たない。二重管理でステータスが食い違うため、各ADRの `ステータス` 欄を唯一の情報源とする。現在有効な決定を見るには次を使う。

```sh
grep -H "^- ステータス:" docs/adr/*.md
```

## テンプレート

テンプレート本体は [`TEMPLATE.md`](./TEMPLATE.md) に分離している。見出しは3つに固定する。増やさない。細分化が必要なら `###` の小見出しを使う。

記入例は [`SAMPLE.md`](./SAMPLE.md)（このリポジトリの実在の決定を書いたもの。AIS-映像間の非同期軌跡マッチングにDTWを採用した根拠）を参照する。

## ステータス

| 値 | 意味 | 実装の根拠にしてよいか |
|---|---|---|
| 提案中 | まだ合意していない | ✗ |
| 採用 | 現在有効な決定 | ✓ |
| 却下 | 検討したが採らなかった。記録として残す | ✗ |
| 非推奨 | まだ動いているが、新規には適用しない | 既存の説明としてのみ |
| 置換済み（ADR-XXXX） | 後続ADRに置き換えられた。歴史的記録 | ✗ |

## 新規作成

1. `ls docs/adr/ 2>/dev/null` で最大番号を確認し、次の連番を採る（欠番は再利用しない。
   まだ1件も無ければ `docs/adr/` を作り、`0001` から始める）
2. `TEMPLATE.md` をコピーして `docs/adr/XXXX-kebab-case-title.md` を作る
3. `./scripts/check-adr-format.sh docs/adr/XXXX-*.md` で検査する。落ちたら指摘箇所を直して
   再実行し、通るまで繰り返す

## 決定が変わったとき

**採用済みADRの「コンテキスト」「決定」を書き換えてはならない。** 何が有効かを一覧から判断できる状態は、この不変性だけが担保している。

1. 新しいADRを起こす
2. 旧ADRのステータスを `置換済み（ADR-XXXX）` へ変える

例外は誤字・リンクの修正と、「結果」への追記（保留事項が解消したときなど）。

## 機械検査で落ちる項目

`scripts/check-adr-format.sh` が pre-commit と ADR編集直後のhookで走る。

- ファイル名が `XXXX-kebab-case.md` でない
- 1行目が `# ADR-XXXX: タイトル` でない
- `- ステータス:` が上の語彙以外、または**但し書きが付いている**
- `- 日付: YYYY-MM-DD` が無い
- 見出しが3つ・この順序になっていない

## 判断が要る部分

検査は書式しか見ない。中身は自分で担保する。

- **「結果」に不利益を書いたか。** 受け入れたトレードオフ・未解決の保留事項・必要な移行作業を、良い面と同じ場所に並べる。ここが空欄に近いADRは、たいてい検討が足りていない
- **ステータスに但し書きを付けたくなったら、それは「結果」に書く内容。** 「採用（ただし〜は保留）」が実際に一覧を使えなくした前例がある
- **単独のADRを起こすほどでない補足・派生決定**は、Y-statements形式の1文を該当ADRの「結果」へ追記する。複数案の比較や移行手順が要る規模なら、新しいADRを起こす

> \<コンテキスト\> において \<懸念\> のため、\<選択肢\> のうち \<決定\> を採る。\<期待する効果\> を得るため、\<受け入れる不利益\> を許容する。

## 形式を変えたくなったら

2026-08-01にNygard形式へ統一した。同じ検討を繰り返さないための記録。

当初は見出しがADRごとに揃わず、ステータスにも「採用（モデル選定は保留）」のような但し書きがあり、**一覧を見ても有効な決定を判別できなかった。** Nygardを採ったのは、見出しが3つに固定されて書くコストが低いこと、ステータスが独立した必須項目であること、「結果」が不利益を書く場所として定義されていることによる。

| 却下した案 | 理由 |
|---|---|
| MADR | ステークホルダー・決定者の欄が個人開発では常に空欄になる。評価軸の分離もこの規模に対して過剰 |
| Y-statements（単独利用） | 検討経緯・却下理由・受け入れた不利益が落ちる。上記のとおり補足用途に限って併用する |

引き換えに、決定要因を評価軸ごとに採点する構造化は得られない。選択肢の比較は却下理由の表に留まる。現在の意思決定の規模ではこれで足りると判断した。
