# ADR-0001: カメラ配信・円形 LCD 表示・推論とダッシュボードを別の機器に分ける

- ステータス: 採用
- 日付: 2026-10-17
- 関連: GitHub Issue #13、Notion 要件定義「機能要件」(REQ-007, REQ-040〜)・「非機能要件」

## コンテキスト

camera 表示中の映像と物体検出の結果を、ダッシュボードで見たい。ダッシュボードには
カメラの全視野(円形 LCD に合わせて切り抜かない)を出し、各機器の状態・検出と通知の履歴・操作もまとめたい。

働いている力:

- 以前は 1 台の Raspberry Pi 3(pi_a)が、カメラ・物体検出(YOLO11n、入力 256)・円形 LCD 表示をすべて担っていた。
  CPU は約 105%(1 コア換算)、SoC は 71–79°C で、スロットリングが起きていた。全視野 640x480 を取得するだけで
  さらに約 128% に上がり、Pi 上で検出やダッシュボード配信を増やす余地はなかった
- 同じ LAN に同型の pi_b と、常時起動している開発 PC(Ryzen 7 7735HS、16 スレッド)がある。どちらも使ってよい
- カメラは pi_b に付け替えた。円形 LCD は pi_a のまま
- ダッシュボードは開発 PC 上のブラウザからだけ見る
- 開発 PC が止まっていても、円形 LCD のカメラ表示は(検出枠なしで)続けたい
- Pi からは mDNS 名(`*.local`)を解決できない

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| pi_a で検出したまま、ダッシュボードだけ pi_b に中継する(この ADR の最初の案) | pi_a の負荷と発熱が下がらない。全視野を出すと pi_a の負荷がさらに増える(実測 約 128%) |
| 検出を pi_b に移す | pi_b も Pi 3 で同じ発熱の問題を抱える。入力 256 のままでは小さな物体を見落とす |
| 開発 PC が描いた LCD 用の画を pi_a に送る | 開発 PC が止まると LCD のカメラ表示も止まる |
| カメラの Pi が JPEG をソフトウェアで作る | Pi 3 で 640x480 の JPEG は 1 枚約 20ms。ハードウェアエンコーダなら CPU をほぼ使わない |

## 決定

**カメラ配信(pi_b)・円形 LCD 表示(pi_a)・推論とダッシュボード(開発 PC のハブ)を別の機器に分ける。**

- pi_b(`camera_server.py`、role camera): Pi 3 のハードウェアエンコーダで、全視野の H.264(640x480、ハブ向け)と
  MJPEG(320x240、LCD 向け)を作り、ポート 8082 で配る。CPU はほぼ使わない
- pi_a(`display.py`、role display): MJPEG を受けて中央の正方形を LCD に出す。ハブから届いた検出結果
  (全視野に対する 0〜1 の座標)を重ねる。ハブが止まっていれば枠なしで映像だけ出す。制御口(ポート 8083)で
  ハブからの操作を受け、状態と吹き出しの通知を返す
- 開発 PC(`hub.py`、role hub、Docker): H.264 を復号して YOLO11n(入力 640)で毎フレーム推論し、結果を pi_a に送る。
  ダッシュボード(127.0.0.1:8090)に、検出枠つきの全視野・各機器の状態・履歴(SQLite)・操作をまとめる
- 接続はすべてハブまたは pi_a から張り、最初に共有トークンで認証する。待ち受けは接続元がプライベート IP でなければ拒否する。
  トークンは各機器の `~/.config/desk-monitor/desk-monitor.env`(600)に置き、リポジトリには入れない

判断の根拠:

1. **Pi の発熱がなくなる。** 推論を開発 PC に移し、映像の符号化をハードウェアに任せた。実測で pi_b は CPU 8%・64°C、
   pi_a は 15%・67°C(全コア合計)。以前の pi_a は 75–79°C だった。
2. **検出の精度と頻度が上がる。** 開発 PC では入力 640 で毎フレーム(実測 52ms/回、約 21fps)推論できる。以前は入力 256 で 1 秒に 1 回。
3. **LCD は開発 PC に依存しない。** 映像は pi_b から pi_a に直接届き、検出枠だけがハブから来る。
4. **全視野をそのまま使える。** 2 本のストリームは同じ全視野(4:3)なので、正規化座標の検出枠を LCD とダッシュボードの両方に重ねられる。

## 結果

- 動作する機器が 3 台になり、デプロイは role ごとに分かれる(`scripts/deploy.sh pi_a` / `pi_b`、`scripts/deploy-hub.sh`)
- Pi が LAN 内で待ち受ける(pi_b: 8082、pi_a: 8083)。以前の非機能要件「ネットワークからの着信を受け付けない」は、
  「LAN 内からトークンで認証した接続だけを受け付ける」に変わる。通信は平文で、トークンと映像は LAN 上を暗号化されずに流れる。
  LAN 内の盗聴は受け入れたリスクとする
- 接続先は IP アドレスで設定する。Pi や PC の IP が DHCP で変わったら `scripts/setup-secrets.sh` の再実行が要る。ルータでの固定を推奨する
- ハブの検出枠は映像に対して、ネットワークと推論の分(約 0.1 秒)遅れて LCD に重なる
- 開発 PC が止まっている間は、検出枠も、検出・通知の履歴も残らない
- カメラの Pi を交換・再配置したら、映像の向きを `camera_server.py` の `--vflip` / `--hflip` で合わせる
