# ADR-0001: カメラ映像のダッシュボードを pi_b に置き、pi_a から外向きに映像を送る

- ステータス: 採用
- 日付: 2026-10-17
- 関連: GitHub Issue #13、Notion 要件定義「機能要件」(REQ-040〜)・「非機能要件」(セキュリティ)

## コンテキスト

camera 表示中の映像と物体検出の結果(LCD と同じ、検出枠とラベルを重ねた 240x240 の画)を、
同じ LAN 内の PC やスマートフォンのブラウザから見たい。合意済みの条件は次のとおり。

- 公開範囲は同じ LAN のみ。インターネットには出さない
- 配信は camera 表示中のみ。face 表示中に裏でカメラや検出を動かさない
- パスワードで制限する

働いている力:

- pi_a(Raspberry Pi 3)は物体検出で CPU 約 105% を使い、SoC 温度は 71–79°C。これ以上の負荷は発熱とスロットリングに直結する
- 非機能要件(セキュリティ)は「ネットワークからの着信を受け付けない」。pi_a にはカメラが付いており、待ち受けポートを開けるとカメラ映像そのものが攻撃面になる
- 同じ LAN に、同型でほぼ遊休の pi_b(Raspberry Pi 3)があり、使ってよいことになった
- pi_a からは mDNS 名(`*.local`)を解決できない

### 検討した選択肢

| 案 | 却下理由 |
|---|---|
| pi_a の表示プロセス内で HTTP サーバを動かし、ブラウザに直接配信する | pi_a に待ち受けポートが必要になり、非機能要件(着信を受け付けない)を変える必要がある。認証処理と閲覧者ごとの送信も pi_a の負荷になる |
| クラウドのサービスに映像を送って公開する | 公開範囲が LAN のみという条件に合わない。カメラ映像を外部に出すことになる |
| 物体検出も pi_b に移し、pi_a は生の映像を送るだけにする | pi_a の発熱は下がる見込みだが、今回の要件(閲覧)の範囲を超える。pi_b は冷却が未確認(アイドルで 61°C)で、ネットワーク遅延や pi_b 停止時に LCD の検出表示が止まる。別途検討する |
| pi_b から pi_a に接続して映像を取りに行く | pi_a が待ち受けることになり、1 つ目の案と同じ問題が残る |

## 決定

**ダッシュボード(Web サーバ)を pi_b に置き、pi_a の表示プロセスが pi_b に外向きに接続して映像を送る。**

- pi_a(`feed.py`): pi_b の feed ポート(8081)に TCP で接続し、最初に共有トークンを送る。pi_b から閲覧者数を受け取り、
  閲覧者がいて camera 表示中のときだけ、LCD に出した画を JPEG にして送る(上限 5fps)。それ以外は約 1 秒ごとに表示モードを送るだけ
- pi_b(`dashboard.py`): 届いた最新フレームを、HTTP(8080)で MJPEG としてブラウザに中継する。Basic 認証をかけ、
  feed・HTTP とも接続元がプライベート IP でなければ拒否する。標準ライブラリだけで書き、pi_b に venv や追加パッケージを入れない
- パスワードとトークンは各 Pi の `~/.config/desk-monitor/*.env`(パーミッション 600)に置き、リポジトリには入れない。
  未設定なら pi_a は送らず、pi_b はダッシュボードを起動しない

判断の根拠:

1. **pi_a は待ち受けポートを持たないまま。** 非機能要件を変えずに済み、カメラ付きの機器の攻撃面が増えない。
2. **閲覧していないときの pi_a の負荷はほぼゼロ。** JPEG を作るのは閲覧者がいるときだけで、送信と変換は別スレッドで行い表示ループを止めない。
3. **閲覧者が増えても pi_a の負荷は変わらない。** 認証・閲覧者ごとの送信は pi_b が受け持つ。
4. **依存を増やさない。** MJPEG はブラウザが `<img>` でそのまま表示でき、サーバ側も標準ライブラリで書ける。

## 結果

- 動作する機器が 2 台になり、デプロイは role(`display` / `dashboard`)ごとに分かれる(`scripts/deploy.sh [host] [role]`)。
  pi_b が止まってもダッシュボードが見られないだけで、pi_a の表示には影響しない
- pi_a は pi_b を IP アドレスで指定する(`feed.env`)。pi_b の IP が DHCP で変わると送れなくなるため、
  pi_b の IP をルータで固定するか、変わったら `scripts/setup-dashboard.sh` を再実行する必要がある
- HTTP は平文で、Basic 認証のパスワードと映像は LAN 上を暗号化されずに流れる。LAN 内の盗聴は受け入れたリスクとする。
  外出先から見たくなったら、ポートを公開せず VPN(Tailscale など)を足す
- pi_a〜pi_b 間も平文で、トークンは盗聴されうる。トークンが漏れると LAN 内の第三者が偽の映像を pi_b に送れる
- 物体検出の pi_b への移設(pi_a の発熱対策)は未検討のまま残る
- pi_b の linger 有効化と秘密情報の配置は、sudo とパスワード入力が要るため人が行う
