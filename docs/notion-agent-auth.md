# Notion CLI(ntn)のエージェント認証

エージェントが `ntn` を実行できる範囲を、Notion 側・Claude 側・実行環境の3層で絞る。

## 方針

- 認証は `NOTION_API_TOKEN`(内部インテグレーションのトークン)を使う。`ntn login`(ユーザーのOAuth)は使わない。
  ユーザー権限はワークスペース全体に及び、`ntn auth token` でトークンも取り出せてしまうため。
- 最も強い境界は **Notion側の共有範囲**。インテグレーションに共有したページ以外は、トークンがあっても触れない。

## セットアップ

1. 内部コネクション(旧称: 内部インテグレーション)を作成する(例: `desk-monitor-agent`)。
   - Notion の名称は「Connection(コネクション)」に変わっている。開発者ポータルの Build > **Internal connections**、
     または 設定 > **Connections** タブ(開発者モードが必要な場合あり)から作成する。
   - **作成できるのはワークスペースのオーナーのみ**。オーナーでない場合は、オーナーに作成を依頼する。
   - 作成後、Configuration タブ(または 「•••」メニュー)から API トークンを取得する。
2. 機能は「コンテンツを読み取る」「コンテンツを更新する」「コンテンツを挿入する」だけにする。ユーザー情報は付与しない。
3. ドキュメント用の index ページを開き、右上「•••」> Connections > **+ Add connection** でこのコネクションを追加する(配下のページにも継承される)。
4. リポジトリ直下の `.env` に `NOTION_API_TOKEN=<トークン>` と書く。`.env` は `.gitignore` で除外済みで、コミットしない。
   引用符は付けない(`--env-file` は引用符も値に含めてしまう)。
5. devcontainer を再ビルドする。`runArgs` の `--env-file` で `.env` がコンテナの環境変数になる。
   **`.env` が無いとコンテナの起動に失敗する**ので、Notion を使わない場合も空の `.env` を作っておくこと。
6. `ntn whoami` で、ボットとして認証されていることを確認する。

## Claude 側の制御(`.claude/settings.json`)

| 区分 | コマンド |
|---|---|
| 許可 | `ntn whoami`、`ntn pages get/edit`、`ntn api v1/pages`、`ntn api v1/blocks/*`、`ntn api ls` |
| 拒否 | `ntn auth`(トークン出力)、`ntn login/logout/update/workers/notion-as-code`、`ntn api ... DELETE`、`printenv`、`env`、`/proc/*/environ` の読み取り |

許可リストにないコマンドは、実行時にユーザーへ確認される。

## 残るリスクと運用

- トークンは環境変数としてコンテナ内のプロセスに渡るため、エージェントが任意のシェルコマンドを実行できる以上、
  完全には隠せない。`printenv` 等の拒否は漏洩しにくくするための多重防御で、境界はあくまで Notion 側の共有範囲。
- そのため、インテグレーションに共有するのはドキュメント用ツリーだけにし、機密ページは共有しない。
- 漏洩が疑われる場合は、Notion のコネクションの画面でトークンを再発行する(旧トークンは即時に無効)。
- `ntn` は Beta のため、サブコマンドや環境変数が変わる可能性がある。更新時に `ntn --help` を確認する。
